SLIDE 04 / 20 · Define the moving parts

What are evals?

A task, a place to do it, and a way to judge the result.

Concrete example. For receipt extraction: the input is a receipt, the environment may be just the model context, and the grader checks the returned fields against a reviewed answer. Valid JSON alone does not mean the total is correct.

Agent version. An agent adds tools and state: goal, actions, state changes, failures or retries, and the final outcome. Save the trace as well as the answer.

Grading. Start with deterministic checks where possible, add domain checks, and use humans or model judges for the parts that require judgment. Judge agreement is something to measure.

SLIDE 06 / 20 · Connect to software design

Tests shape the software

Tests create feedback while we build.

Familiar ideas. Unit tests isolate a behavior. Integration tests exercise the connections. Property tests check invariants across many inputs: for example, totals reconcile or a transformation preserves information.

Rich Hickey connection. Ease of writing and simplicity of the result are different. Fewer lines can improve readability, but line count is only a proxy. A short abstraction can hide tightly coupled behavior; a larger collection of tiny pieces can also become difficult to hold in your head.

Apply it to AI. Give components clear inputs and outputs, isolate dependencies, and preserve intermediate results. Testability becomes evalability. Keep this connection short; this is an AI talk.

SLIDE 07 / 20 · Expand beyond a score

Evals in AI powered software

Evals help decide where to put boundaries.

Component and system. A single end-to-end score tells you something broke. Component evals help distinguish retrieval failures, extraction mistakes, bad tool calls, and incorrect final reasoning. Keep the full-system eval as well.

Observability bridge. An HTTP 200 and well-formed JSON can still contain the wrong answer. Capture inputs, outputs, tool calls, errors, latency, cost, and model/prompt versions. You cannot inspect an output you never saved.

Complexity budget. Add another agent, retry loop, or retrieval stage when measured results justify it. More machinery gives you more failure surfaces and more behavior to diagnose.

SLIDE 08 / 20 · Use retrieval as the example

Evaluate RAG retrieval

Nearest in embedding space is not the same as useful evidence.

Failure cases. Try paraphrases and domain language alongside exact product IDs, dates, and names. Chunk boundaries can split the evidence you need. Filters and approximate search can hide a relevant result before generation even starts.

Fair comparison. Use the same corpus, queries, and relevance labels for keyword, semantic, and hybrid retrieval. Include query embedding in latency and cost. Choose the implementation from the measured workload.

Two levels. Precision asks how much of what we returned was useful; recall asks how much useful material we found. Then separately evaluate the final answer: good retrieval does not guarantee faithful use of the evidence.

SLIDE 09 / 20 · Transition

Optimization

Once we can measure, we can improve deliberately.

Set up the choices. Prompt optimization changes instructions. SFT changes weights using example answers. RL changes weights using rewards from attempts. They can share tasks and grading infrastructure without being the same procedure.

Avoid a ladder. These are tools for different bottlenecks, not mandatory stages every application must progress through.

SLIDE 10 / 20 · Choose the target carefully

Hillclimbing starts with a metric

A metric makes iteration possible; it also directs behavior.

Define success. Accuracy, pass rate, cost per ticket, or trigger rate are useful only with a clear denominator and a connection to the product goal. A high trigger rate is not automatically a good result.

Guardrails. Optimize cost subject to a quality threshold, or improve quality within a latency budget. Inspect failure categories so an aggregate gain does not conceal a worse outcome for an important subset.

SLIDE 11 / 20 · Explain the discipline

The hillclimbing loop

One change, a hypothesis, and evidence beyond run noise.

Baseline. Repeat runs to understand variability. Freeze the other moving parts and record the model, prompt, data, scorer, and harness versions.

Look at failures. Use development examples and traces to form a specific hypothesis. Compare the proposed change against the baseline, including regressions and cost.

Holdout nuance. Do not expose test examples to the prompt analyzer. Repeatedly choosing candidates based on the same held-out score also leaks information through selection. Use validation for iteration and reserve a separate untouched final test when possible.

SLIDE 12 / 20 · Answer “how does it mutate?”

GEPA (prompt optimization)

An LLM reads the failure and writes a candidate prompt.

Mechanism. Give the reflection model the current prompt, example inputs, model outputs or tool traces, and grader feedback. Ask it to explain a failure pattern and propose revised instructions. The mutation is generated text, not a gradient update to the task model.

Example. If invoice extraction confuses subtotal and total due, feedback can motivate an instruction that distinguishes those fields and handles missing values. Run the candidate on the dataset; a plausible explanation is not evidence that it works.

What survives. Keep candidates because they improve measured behavior and generalize, not because the rewritten prompt sounds more sophisticated. This slide simplifies the broader GEPA candidate-search process.

SLIDE 13 / 20 · Bound the takeaway

GEPA (prompt optimization) results on IFBench

Prompt optimization can be surprisingly effective.

Explain the plot. The lines and circles use the validation axis; the stars use the separate test axis. The curves are approximate reconstructions. This comparison is a result on a particular model and instruction-following benchmark.

Decision point. Try extracting existing capability with better instructions before paying for training. A plateau can also come from missing context, poor tools, bad labels, or a weak scorer; it does not by itself prove the model is too small.

Capacity intuition. Parameter count alone does not tell us what can be elicited. Small models can be excellent at narrow tasks, while training still depends on the base model, data, and task difficulty.

SLIDE 15 / 20 · Tie quality to economics

Hillclimbing for cost reduction

Better instructions can make a cheaper model viable.

Tell the story. The example combines prompt improvements and model/effort choices. It is not evidence of fine tuning. Explain the adopted path rather than attributing every gain to one technique.

Small-data nuance. Look at the held-out result alongside the development score. A small set is a useful starting point, but it leaves uncertainty; add representative cases and production failures over time.

What to measure. Include retries, review work, and failed attempts in the business cost. A low token bill is not a win if the workload now needs more human cleanup.

SLIDE 16 / 20 · Use the extraction example

Supervised fine tuning

Reviewed eval examples can become training examples.

Same shape, different use. For a one-shot task, both can look like receipt or invoice input → gold JSON output. Training examples teach the mapping; held-out examples measure whether it generalizes. Keep those sets separate.

When SFT fits. Reach for SFT when a stable narrow task needs consistent formatting or behavior, enough reviewed examples exist, and prompt optimization has stopped delivering useful gains. A smaller specialized model may improve deployment economics; measure that instead of assuming it.

Qualify the slide. Loss of general capability is a risk, not an inevitable cliff. Watch for forgetting, overfitting, and distribution shift. A specialist can be a good trade when its role is deliberately bounded.

Data quality. A failed rollout is not automatically a gold answer. Review or correct outputs before using them as targets. Keep improving the dataset rather than teaching yesterday’s mistakes.

SLIDE 17 / 20 · Contrast with demonstrations

Reinforcement learning

RL learns from the reward on an attempt.

Why an environment. The model acts, tools change the state, and a grader evaluates the outcome. There may be several valid ways to succeed, so a complete reference trajectory is not always necessary.

When to consider it. RL is attractive for sequential behavior with reliable rewards and a realistic, repeatable environment. First establish that the failures are behavior you can train, rather than missing information or broken tools.

Harness connection. Harbor-style tasks can support both evaluation rollouts and RL training. Shared environments and graders are valuable, but evaluation alone does not update weights; you still need the training machinery.

Hard parts. Reset state, isolate runs, keep tools faithful to production, and test whether the reward can be gamed. A higher reward is useful only if it still corresponds to the outcome you wanted.

SLIDE 18 / 20 · Focus on the harness

RL at Ramp

A narrow agent task gives training a concrete target.

Walk the example. The agent answers questions by operating over a spreadsheet. Talk about the tool interface, synthetic task generation, and an outcome grader as part of the system design.

Read the table. Compare the specialized model with its own base model, then with the other models under this harness. Keep accuracy and elapsed time separate: a timing ratio above 1 means more time than Haiku, not greater speed.

Transfer the lesson. The interesting pattern is a task distribution plus executable feedback. A result on this workload is not a claim that the specialist is better at every task. Synthetic examples still need checks for realism and coverage.
